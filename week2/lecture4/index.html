    Week 2 — Lecture 2: SystemC¶

    Course: Advanced Digital Design and Verification
    Instructor: Sneh Saurabh • Date: 21 Aug 2025
    Topic: Modules, processes, events, signals, and notifications in SystemC

    Key Takeaways

    • Modules (SC_MODULE) are the building blocks of SystemC; contain ports, channels, processes, and other members.
    • Constructors (SC_CTOR) initialize and connect sub‑designs, register processes, and set sensitivities.
    • Processes can be SC_METHOD or SC_THREAD, with different rules for suspension and persistence.
    • Simulation involves evaluate/update cycles; kernel is cooperative multitasking.
    • Events (sc_event) allow synchronization between processes; used with notify() and wait().
    • Sensitivity can be static (declared at elaboration) or dynamic (changed at runtime).
    • Signals (sc_signal<T>) follow the evaluate/update model and embody delta cycles.
    • Notifications can be immediate or delayed (after update phase).

    1) Modules¶

    classDiagram

    +ports

  }

  SC_MODULE <|-- UserModule

    +alloc_subdesigns()

    • Modules are C++ classes inheriting from sc_module.
    • Organized as .h for declaration, .cpp for implementation.
    • Contain: constructor, ports, submodules, channels, member data, processes.

    2) Module constructor¶

    SC_MODULE(my_mod) {
  SC_CTOR(my_mod) : init_list {
    // allocate submodules
    // connect ports ↔ channels
    // register processes with kernel
    // set sensitivity
  }
};

    flowchart TB
  A[Constructor] --> B[Allocate submodules]
  A --> C[Connect submodules]
  A --> D[Register processes]
  A --> E[Set static sensitivity]
  A --> F[Misc setup]

    3) Module hierarchy¶

    SC_MODULE(Bottom) {
  SC_CTOR(Bottom) { cout << name() << endl; }
};

SC_MODULE(Mid) {
  Bottom b1, b2;
  SC_CTOR(Mid) : b1("b1"), b2("b2") {}
};

SC_MODULE(Top) {
  Mid mid;
  Bottom b;
  SC_CTOR(Top) : mid("mid"), b("b") {}
};

    flowchart TB
  Top --> Mid
  Top --> B
  Mid --> B1
  Mid --> B2
    • Instances of submodules are declared as data members of the parent.
    • new/delete operators can create/destroy modules dynamically.

    4) Simulation processes¶

    • Kernel schedules execution; cooperative, non‑preemptive.
    • Registered via SC_THREAD or SC_METHOD.
    Property SC_THREAD SC_METHOD
    Suspension wait() allowed Cannot wait(); uses next_trigger()
    Behavior Like software thread, persistent state Like function, no persistence
    Registration SC_THREAD(func) SC_METHOD(func) 
    classDiagram
  class SC_THREAD {
    +persistent vars
    +suspension via wait()
  }
  class SC_METHOD {
    +no persistence
    +reactive to sensitivity
  }

    5) Process syntax example¶

    SC_MODULE(proc) {
  void th(){ while(1){ cout<<"th @"<<sc_time_stamp(); wait(500,SC_MS);} }
  void me(){ cout<<"me @"<<sc_time_stamp(); next_trigger(200,SC_MS);}
  SC_CTOR(proc){ SC_THREAD(th); SC_METHOD(me); }
};
    • th prints every 500 ms.
    • me prints every 200 ms.
    • Simulation ends at 1500 ms.

    6) Simulation engine¶

    flowchart LR
  A[Elaboration] --> B[Initialize]
  B --> C[Evaluate]
  C --> D[Update]
  D -->|if events| C
  D -->|else| E[Advance Time]
  E --> B
  E -->|if none| F[Cleanup]
    • Evaluate/Update: all runnable processes execute one at a time.
    • Processes return by end of function or wait().
    • Delta cycles = repeated evaluate/update at same time.

    7) Events¶

    • sc_event represents a zero‑time notification.
    • Has no value and no duration.
    • Trigger: event.notify().
    • Wait: wait(event).
    sequenceDiagram
  participant T as Thread A
  participant E as Event
  participant M as Thread B
  T->>E: notify()
  M->>E: wait(event)
  E-->>M: resumes immediately or scheduled

    8) Event example¶

    SC_MODULE(two) {
  sc_event given, taken;
  void give(){ while(1){ wait(500,SC_MS); cout<<"given"<<sc_time_stamp(); taken.notify(100,SC_MS);} }
  void take(){ while(1){ wait(given); cout<<"taken"<<sc_time_stamp(); }}
  SC_CTOR(two){ SC_THREAD(give); SC_THREAD(take); }
};
    • Two threads coordinate via events.
    • give notifies taken after 100 ms.
    • take waits for given.

    9) Sensitivity¶

    Type Declared Behavior
    Static in constructor with sensitive << sig set at elaboration
    Dynamic via next_trigger() or wait(event) can change at runtime 
    SC_METHOD(toggle);
sensitive << edge;

    flowchart TB
  S[Static Sensitivity] --> F[Fixed at elaboration]
  D[Dynamic Sensitivity] --> R[Runtime changeable]

    10) Signals¶

    • Primitive channel sc_signal<T> implements evaluate/update.
    • Two values: current and new.
    • write(T) = schedule new value.
    • read() = fetch current value.
    flowchart LR
  P1[Process 1] -->|write(x)| SIG[sc_signal]
  SIG -->|visible after update| P2[Process 2]

    11) Signal member functions¶

    • value_changed_event(): returns event triggered on update.
    • event(): check if change happened in last delta cycle.
    • Special events for sc_signal<bool> and sc_signal<sc_logic>:
    • posedge_event(), negedge_event().
    • sc_buffer<T>: like signal but event fires on every write.

    12) Immediate vs Delayed notification¶

    Type Function Effect
    Immediate notify() triggers before update
    Delayed notify(SC_ZERO_TIME) triggers after update (next delta) 
    sequenceDiagram
  participant P as Process
  participant E as Event
  P->>E: notify()
  Note over E: Immediate, before update
  P->>E: notify(SC_ZERO_TIME)
  Note over E: Scheduled after update
