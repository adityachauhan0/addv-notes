    Week 3 — Lecture 1: SystemC¶

    Course: Advanced Digital Design and Verification
    Instructor: Sneh Saurabh • Date: 26 Aug 2025
    Topic: Communication in SystemC: Interfaces, Ports, Channels, and Testbenches

    Key Takeaways

    • Communication in SystemC is modeled using interfaces, ports, and channels, enabling modular and reusable design.
    • Interfaces define what services are provided (abstract methods); channels define how those services are implemented.
    • Ports allow modules to access channels without knowing the implementation, maintaining encapsulation.
    • sc_port, sc_export, and specialized ports (sc_in, sc_out, sc_inout) provide flexible modeling constructs.
    • Testbenches in SystemC simulate complete systems by driving inputs and observing outputs, allowing debugging via waveforms and VCD dumps.

    1) Interfaces, Channels, and Ports¶

    1.1 Interfaces (Abstract Services)¶

    • An interface is an abstract class derived from sc_interface.
    • Provides pure virtual functions — must be implemented by a channel.
    • Interfaces decouple communication definition from implementation.
    class my_interface : public sc_interface {
public:
  virtual int read(void) = 0;   // service 1
  virtual void write(int i) = 0; // service 2
};

    1.2 Channels (Concrete Implementations)¶

    • A channel is a class that derives from sc_channel or sc_prim_channel.
    • Implements all abstract methods of the interface.
    • Can store state (e.g., data variables).
    class my_channel : public sc_prim_channel, public my_interface {
  int data;
public:
  int read(void) override { return data; }
  void write(int i) override { data = i; }
};

    1.3 Ports (Access Points)¶

    • A port is a SystemC class templated by an interface type.
    • Declared as a data member inside a module.
    • Enables a module to invoke methods of a channel through the interface.
    SC_MODULE(computation) {
  sc_port<my_interface> marks_po;
  sc_port<my_interface> grade_po;
  void compute();
  SC_CTOR(computation) { SC_THREAD(compute); }
};

    2) Binding Ports and Channels¶

    Steps: 1. Instantiate module(s). 2. Instantiate channel(s). 3. Bind port(s) to channel(s).

    my_channel nc_marks, nc_grade;
computation comp("comp");
comp.marks_po(nc_marks);   // port bound to channel
comp.grade_po(nc_grade);
    • Ports behave like pointers to channels.
    • Channels must implement the interface required by the port.
    flowchart LR
  M[Module] -->|port| P[sc_port]
  P -->|binds| C[Channel]
  C -->|implements| IF[Interface]

    3) Example: Computation Module¶

    SC_MODULE(computation) {
  sc_port<my_interface> marks_po, grade_po;
  void compute() {
    int m = marks_po->read();
    int g;
    if (m > 80) g = 9;
    else if (m > 60) g = 7;
    else g = 5;
    grade_po->write(g);
  }
  SC_CTOR(computation) { SC_THREAD(compute); }
};
    • The module does not know how data is stored in the channel.
    • It simply calls read() and write() on the port.
    • Encourages modularity and reusability.

    4) sc_export¶

    • sc_export<T> allows exposing a channel defined inside a module to the outside world.
    • Syntax similar to sc_port<T>.
    SC_MODULE(M1) {
  sc_export<my_interface> e1;
  my_channel ch1;
  SC_CTOR(M1) : e1("e1") { e1(ch1); } // bind export to channel
};
    • External modules can now access M1's channel via the export.

    5) Specialized Ports¶

    • sc_in<T>: input port, exposes read(), event(), value_changed_event().
    • sc_out<T>: output port, exposes write().
    • sc_inout<T>: bidirectional.

    Specialized for bool and sc_logic: - posedge_event(), negedge_event() → return event on transitions. - pos_edge(), neg_edge() → return boolean.

    6) Example: Inverter Connection¶

    SC_MODULE(INV) {
  sc_in<bool> A;
  sc_out<bool> Z;
  void compute(){
    while(1){
      Z.write(!A.read());
      wait(A.value_changed_event());
    }
  }
  SC_CTOR(INV) { SC_THREAD(compute); }
};

SC_MODULE(top) {
  sc_in<bool> A_top;
  sc_out<bool> Z_top;
  INV I1, I2;
  sc_signal<bool> s;
  SC_CTOR(top) : I1("I1"), I2("I2") {
    I1.A(A_top); I1.Z(s);
    I2.A(s); I2.Z(Z_top);
  }
};

    flowchart LR
  A_top --> I1[INV] --> s[Signal] --> I2[INV] --> Z_top
    • Two inverters connected in series.
    • Signal s serves as an internal wire.

    7) Testbench Construction¶

    SC_MODULE(Testbench) {
  sc_signal<bool> s_in, v_out;
  top DUT;

  void apply_stimulus(){
    wait(SC_ZERO_TIME);
    s_in.write(true); wait(1, SC_SEC);
    s_in.write(false); wait(1, SC_SEC);
    s_in.write(true); wait(1, SC_SEC);
  }

  void report(){
    while(1){
      cout << "Input=" << s_in.read()
           << " Output=" << v_out.read()
           << " @ " << sc_time_stamp() << endl;
      wait(s_in.value_changed_event());
    }
  }

  SC_CTOR(Testbench) : DUT("top") {
    DUT.A_top(s_in);
    DUT.Z_top(v_out);
    SC_THREAD(apply_stimulus);
    SC_THREAD(report);
  }
};
    • Stimulus applied at different times.
    • Report process prints signal values during simulation.

    8) Testbench Output¶

    • After a few delta cycles, signals stabilize.
    • Useful for functional verification.
    • Can also dump waveforms to VCD for viewing.
    Input=0 Output=1 @ 0 s
Input=1 Output=0 @ 1 s
Input=0 Output=1 @ 2 s
Input=1 Output=0 @ 3 s

    9) Summary¶

    • Interfaces: define abstract services.
    • Channels: implement interfaces and hold data/state.
    • Ports: allow modules to use interfaces without coupling.
    • Exports: expose internal channels externally.
    • Special ports: simplify signal-driven modeling.
    • Testbenches: simulate systems by applying input patterns and observing outputs.
